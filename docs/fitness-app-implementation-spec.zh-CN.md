# 个人训练规划与记录 App：产品及技术实现规格

> 文档版本：v1.2-single-workout-plan  
> 日期：2026-08-05  
> 目标读者：产品、交互、客户端、后端、数据、测试及动作内容维护人员  
> 文档状态：核心产品约束已确认，可以据此拆分开发任务

## 1. 结论先行

这款产品定位为“离线优先、可组合、可追溯的个人训练执行系统”，不是医疗诊断工具，也不是社交健身平台。

推荐的第一版技术路线：

- 客户端统一采用 Flutter，首发 iOS + Windows；暂不开发 macOS 客户端。iOS 的编译、签名和发布仍需要 macOS/Xcode 构建环境。
- 本地采用 SQLite；用户必须先登录激活设备，之后在断网但本地会话有效时，所有核心训练功能仍可使用。
- 服务端部署在中国大陆，采用 PostgreSQL + 对象存储 + 鉴权 + 自有同步/管理 API；基础设施保持供应商中立，可落在阿里云、腾讯云或其他境内云。
- 个人训练数据与公共动作库使用不同的同步策略：个人数据以用户为权威、多端合并；公共动作库以服务端发布版本为权威、客户端只读更新。
- 动作库不是单一目录树。每个动作具有一个“训练阶段用途”和多组正交标签，支持从物理治疗、功能性训练及力量训练等不同视角检索。
- 训练计划由可拖拽的阶段块、动作槽位、处方及替代动作构成；开始训练时生成不可变快照，确保历史记录不因动作或计划更新而变化。
- 重量调整只做“可解释的建议”，默认使用目标次数区间 + RIR/RPE + 最小器械增量，不在未经用户确认时自动改计划。
- 桌面端提供动作库草稿、审核、预览、发布、回滚、批量导入和媒体管理；生产库严禁直接编辑。

## 2. 产品目标与非目标

### 2.1 目标

1. 用户可以快速设计训练计划，并从动作库插拔动作或整个训练阶段。
2. 训练中可以用尽量少的点击记录实际重量、次数、RPE/RIR、疼痛和备注。
3. 系统基于历史表现给出保守、透明、可撤销的下次重量建议。
4. 动作库能通过图片、短视频、分步骤文字、提示和常见错误清楚说明动作。
5. iOS 与桌面端可以离线工作，并在恢复网络后安全同步。
6. 动作内容可以持续修订、审核、灰度发布和回滚，同时不破坏旧计划和历史训练。
7. 用户可以完整导出和删除自己的数据，不被单一云服务锁定。

### 2.2 第一版不做

- 不诊断伤病，不根据疼痛自动给出治疗方案，不代替医生或物理治疗师。
- 不承诺纠正体态、治疗疾病或避免受伤。
- 不做公开社区、排行榜、教练商城、付费课程和多人协作。
- 不做基于摄像头的动作姿态识别。
- 不自动生成个体化康复处方。
- 不把卡路里消耗作为核心准确指标。
- 不让 AI 直接发布动作内容或修改训练负荷；AI 生成内容必须进入人工审核流程。

## 3. 已确认的产品决定

以下决定已由产品负责人确认，是首版实现约束；变更时必须同步修改架构、排期和验收范围。

| 决定 | 已确认方案 | 实现影响 |
|---|---|---|
| 桌面平台 | Windows 首发，暂不做 macOS 客户端 | 桌面交互、安装包、签名和测试以 Windows 为准；iOS 另行使用 macOS/Xcode 构建 |
| 产品范围 | 个人使用优先，数据结构和权限保留未来多用户能力 | 首版不做社交/协作，但从第一天按 `user_id` 隔离数据 |
| 登录策略 | 必须登录；首次登录后允许有效离线会话 | 首次使用需要网络；离线不能切换账号、注册或找回密码，但可以训练和记录 |
| 服务部署 | 中国大陆境内部署 | 使用境内 PostgreSQL、对象存储和 CDN，评估备案、等保及个人信息保护要求 |
| 动作媒体 | 由产品负责人自行上传 | 后台提供上传、转码、版权声明、版本和撤回能力，不依赖外部视频链接 |
| 内容审核 | 由产品负责人自行审核并发布 | 首版允许作者自审，但必须完成检查清单并保留审计记录；未来可增加独立审核角色 |

## 4. 用户与关键场景

### 4.1 角色

- 训练者：创建计划、执行训练、查看趋势、维护个人动作。
- 动作编辑者：由产品负责人承担，在 Windows 桌面端创建和修订动作草稿、上传自有媒体。
- 审核者：首版由产品负责人承担，检查内容准确性、安全提示、版权和媒体质量；未来可以授予独立人员。
- 管理员：管理分类、发布版本、回滚、用户角色和审计日志。

一个账号可以同时具备多个角色。客户端普通界面不展示后台能力；桌面端只有取得相应声明的账号才显示“动作库管理”。

### 4.2 核心用户旅程

1. 第一次打开：登录 → 选择单位、可用器械、主要目标和经验水平；未登录不能进入个人训练数据。未来开放自助注册时，注册完成后进入同一流程。
2. 建计划：新建一次训练计划 → 添加阶段块 → 从动作库拖入动作 → 为每个动作设置独立处方和替代动作 → 保存版本。
3. 开始训练：选择一个训练计划 → 填写可选状态 → 系统复制该计划版本快照 → 按阶段、逐组记录 → 完成总结 → 确认下次调整。
4. 临场替换：器械占用或身体不适 → 查看同模式/同目标替代动作 → 仅本次替换或同步修改以后计划。
5. 维护动作：桌面端创建草稿 → 补齐标签与媒体 → 规则校验 → 审核 → 发布新动作库版本 → 客户端增量更新。
6. 换设备：登录 → 拉取个人数据和动作库清单 → 本地合并 → 媒体按需缓存。

## 5. 训练学与动作库模型

### 5.1 分类原则

不要把“拉伸、胸、杠铃、初级”混进同一棵分类树。动作应同时拥有：

- 一个主要训练阶段用途；
- 零到多个次要用途；
- 多组正交标签；
- 可选的风险提示、限制条件和替代关系。

这样同一个“弹力带肩外旋”可以用于激活、动作准备或辅助训练，而不必复制成三个动作。

### 5.2 主要训练阶段用途

| 编码 | 中文名 | 定义与例子 |
|---|---|---|
| `readiness` | 状态检查 | 呼吸、疼痛/疲劳自评、简单活动度检查；不是诊断性评估 |
| `general_warmup` | 一般热身 | 提高体温和心率，如划船机、单车、轻松慢跑 |
| `mobility` | 活动度/动态拉伸 | 主动或动态关节活动；静态拉伸用标签单独标记 |
| `activation_control` | 激活与神经肌肉控制 | 低负荷控制、稳定、呼吸和本体感觉练习 |
| `movement_prep` | 专项动作准备 | 与主项模式接近的技术准备、递增热身组、低强度跳跃/投掷 |
| `power_skill` | 爆发力与技术 | 对速度、协调或技术质量要求高，通常在疲劳较低时执行 |
| `primary_strength` | 主项力量 | 当日优先的高价值力量动作 |
| `accessory` | 辅助力量/肌肥大 | 补充训练量、肌群或动作模式的动作 |
| `local_endurance` | 局部肌耐力 | 以局部持续做功能力为主要目标 |
| `conditioning` | 能量系统/有氧 | 稳态、间歇、冲刺、循环训练 |
| `cooldown_recovery` | 整理与恢复 | 低强度降速、呼吸、轻柔活动度；不承诺加速恢复 |

阶段名称允许用户自定义，但内部编码固定。一次训练计划可以缺少任何阶段；系统不强迫所有计划套用完整流程。

### 5.3 正交标签维度

每个标签都属于一个固定维度，避免自由文本失控：

- 目标：最大力量、肌肥大、爆发力、肌耐力、有氧基础、无氧能力、活动度、稳定性、技术学习、恢复。
- 动作模式：蹲、髋铰链、水平推/拉、垂直推/拉、携行、旋转、抗旋转、屈曲/伸展、步态/跑跳、呼吸。
- 身体区域：全身、躯干、肩带、肩、肘、腕手、髋、膝、踝足；可进一步关联肌群，但不以“孤立某块肌肉”替代动作模式。
- 运动平面：矢状、额状、水平、多平面。
- 动力链：开放链、闭合链、混合。
- 侧别：双侧、单侧、交替、偏侧负重。
- 起始姿势：站、坐、仰卧、俯卧、侧卧、跪、半跪、四点支撑、悬垂。
- 器械：徒手、杠铃、哑铃、壶铃、器械、绳索、弹力带、药球、悬吊、雪橇、有氧器械等。
- 负荷类型：外部重量、自重、辅助自重、弹性阻力、等长、速度/距离/时间。
- 技能等级：入门、基础、中级、高级；等级描述技术复杂度，不等同于训练者身份。
- 冲击等级：无/低/中/高。
- 拉伸方式：动态、静态、主动、被动、PNF；仅在适用时设置。
- 环境限制：所需空间、是否需要固定点、是否需要保护者、噪音/冲击。

标签是筛选维度，不直接推导医疗适应证。

### 5.4 每个动作的内容要求

发布一个动作至少需要：

- 稳定动作 ID、中文名、英文名、别名；
- 一句话目的说明；
- 主要用途、动作模式、身体区域、器械、难度；
- 起始姿势、逐步执行、呼吸建议、节奏说明；
- 3–6 条关键提示，2–5 条常见错误；
- 停止条件和一般安全提示；
- 记录方式：重量次数、时间、距离、能量、等长时长或组合；
- 至少一种自有/已授权媒体；
- 内容作者、审核者、来源、版权、版本与变更说明。

可选字段包括回归动作、进阶动作、同类替代、左右侧说明、适用器械规格和无障碍替代文本。

### 5.5 媒体规范

- 首选 6–20 秒、可循环、无背景音乐的 MP4/H.264 或 H.265；同时生成封面 WebP/JPEG 和 2–4 张关键帧。
- 视频至少提供正面或侧面中最能说明动作的一种视角；复杂动作可有多视角。
- 不依赖第三方网页播放器；外链只保存在“参考来源”，不作为唯一教学内容。
- 原始媒体进私有审核桶；发布后生成不可变对象路径及 CDN 版本。
- 保存宽高、时长、编码、大小、SHA-256、版权人、许可类型、许可到期日和替代文本。
- 客户端默认只下载封面；视频按需播放和缓存，设置中允许清理缓存、Wi-Fi 下预下载。
- 媒体删除采用撤回而非覆盖；已下载内容应按撤回清单失效。

### 5.6 内容安全边界

- “注意”“不适合”“停止条件”属于一般教育内容，不得表述为个体医疗判断。
- 不使用“保证不受伤”“修复骨盆”“治疗肩袖”等未经支持的承诺。
- 若记录到胸痛、晕厥、严重呼吸困难、突发神经症状或明显急性损伤，应用停止训练流程并建议寻求合格专业人员/急救帮助；不要继续给负荷建议。
- 一般疼痛评分只用于个人记录。系统不能只凭一个分数诊断或开具康复计划。
- 孕产期、未成年人、术后、心血管/代谢疾病、神经系统疾病等人群不套用通用自动处方。

## 6. 插拔式计划模型

### 6.1 结构

```text
Plan
└── PlanVersion（保存后不可变）
    └── StageBlock（有序阶段块）
        ├── ExerciseSlot（动作槽位）
        │   ├── ExerciseRef（默认动作）
        │   ├── Prescription（处方）
        │   └── Alternatives（替代规则/动作）
        └── Group（普通、超级组、循环、巨型组）
```

`Plan` 的用户语义是“一次完整训练模板”，而不是周计划或多个训练日的容器。阶段是计划内唯一的第一层可编辑结构。日历安排、周期与重复规则属于未来独立功能，不能反向在 `Plan` 内引入训练日。

### 6.2 阶段块

阶段块可以：

- 从动作库逐个添加动作；
- 从个人模板插入一整个热身、主项或有氧块；
- 拖拽排序、复制、折叠、启用/停用；
- 保存为可复用模块；
- 设置阶段级目标时长、组间转换时间和完成规则。

插入模块时默认为“复制并断开”，避免以后修改模板意外改变现有计划；用户可显式选择“保持关联”，关联更新必须展示差异并确认。

### 6.3 动作槽位与处方

动作槽位不是简单的动作 ID，还包含：

- 目标类型：固定组次、次数范围、AMRAP、EMOM、按时、按距离、自由记录。
- 组数、次数下限/上限、目标 RPE 或 RIR、节奏、休息、目标重量或强度百分比。
- 递增热身组、工作组、回退组、递减组等组类型。
- 每侧/合计语义，单侧动作的左右记录规则。
- 完成标准、失败处理和备注。
- 可用器械与最小增量。
- 替代动作及替代条件：同模式、同目标、同器械或人工指定。

处方字段按记录类型显示。例如跑步不出现“次数”，平板支撑不强迫填写“重量”。

### 6.4 版本和快照

- 每次发布计划生成新的 `PlanVersion`，旧版本不可原地修改。
- 训练开始时创建 `WorkoutSession`，将动作名称、关键参数、处方、单位及动作版本复制到快照。
- 训练中调整仅影响本次快照；结束时询问是否把变化应用到下个计划版本。
- 删除或下架动作不会破坏历史，历史继续显示快照；新计划中标记“已下架，建议替换”。

## 7. 重量调整与训练反馈

### 7.1 必须记录的两套数据

- 计划值：计划重量、组数、次数范围、目标 RPE/RIR、休息。
- 实际值：每组实际重量、次数、RPE/RIR、是否完成、疼痛、技术备注、开始/结束时间。

不覆盖计划值，否则无法比较执行偏差。

### 7.2 默认建议算法：双重渐进

算法按每个动作槽位独立运行，版本化保存。默认规则：

1. 只有工作组进入计算，热身组和明确标记的测试组不参与。
2. 若所有工作组达到次数上限，RIR/RPE 达标，且没有疼痛/技术失败标记，则建议增加一个“器械最小增量”或配置的百分比。
3. 若完成范围中部且主观强度达标，建议维持。
4. 若多组低于次数下限、明显超过目标强度，或用户标记技术失败，建议维持或小幅降低。
5. 若用户记录疼痛或停止条件，暂停自动加重，只展示“请人工确认”的原因。
6. 建议必须显示依据，例如“3 组均达到 10 次，目标 RIR 2，实际 RIR 2–3”。用户可接受、改写或忽略。

默认百分比仅作为可配置起点：上肢 2%–5%、下肢 2.5%–5%，最终舍入到实际器械增量。不要把这些默认值写死在领域模型中。

### 7.3 其他算法

- 固定线性加重：适合用户自行选择的简单方案。
- RPE/RIR 自我调节：根据目标强度建议当日重量区间。
- 百分比训练：引用已确认的训练最大值，不默认等同真实 1RM。
- 估算 1RM：可选显示 Epley 等公式，仅用于趋势；保存公式版本和适用次数限制。
- 时间/距离进阶：速度、坡度、阻力、工作/休息比等维度分别配置。

所有算法通过统一 `ProgressionPolicy` 接口实现，不将业务规则散落在界面代码中。算法输出是建议对象而不是直接写回计划。

### 7.4 特殊负荷语义

数据模型必须区分：

- 总重量与单只哑铃重量；
- 是否包含杠铃杆重量；
- 自重、自重加负重、辅助重量（辅助越大难度越低）；
- 每侧重量与总重量；
- 器械标称重量与实际配重；
- 公斤和磅的原始输入。

数据库保存 SI 基准值与原始显示值/单位，避免来回换算造成漂移。

## 8. 信息架构与界面

### 8.1 iOS 导航

底部五栏：

1. 今日：下次训练、快速开始、状态和恢复中的训练。
2. 计划：计划列表、日历、模板和计划编辑。
3. 动作库：浏览、搜索、收藏、个人动作。
4. 进度：训练量、动作趋势、频率、个人纪录和数据质量说明。
5. 设置：账号、同步、单位、器械、提醒、导入导出、隐私。

训练执行页全屏显示，不受底部导航干扰；主要按钮适合单手点击，支持锁屏/后台计时恢复。

### 8.2 桌面导航

左侧导航栏：今日、计划编辑器、动作库、历史与分析、数据、动作库管理（有权限时出现）。

计划编辑器采用三栏：

- 左：动作库与筛选；
- 中：单次训练画布和阶段块；
- 右：所选动作的处方、替代和说明。

支持拖放，也必须支持键盘和“添加到…”菜单，不能让拖放成为唯一操作。

### 8.3 视觉语言

“雅黑”解释为深色、克制、精致，而不是纯黑大面积加细灰线：

- 背景：`#0E1013`；一级表面：`#171A1F`；二级表面：`#20242B`。
- 主文字：`#F2F4F7`；次文字：`#AAB1BC`；分隔：`#2C323B`。
- 主强调色建议青绿色 `#5DD6B0`；警告、疼痛和危险使用独立语义色。
- 12–16 px 圆角、清晰的表面层级、少量柔和阴影/描边；不用大面积纯渐变。
- 用动作封面、阶段色条、训练进度环和微交互增加质感，但不让装饰抢过记录操作。
- 中文使用系统字体（iOS 为苹方，Windows 为微软雅黑/系统回退），数字使用等宽特性便于重量对齐。
- 支持系统深色/更深色、动态字号、降低动态效果、高对比度和色盲可辨识状态。

### 8.4 关键页面状态

每个页面都必须设计：首次空状态、加载、离线、部分失败、权限不足、同步冲突、内容已下架和重试状态。训练记录不能因页面关闭、来电、崩溃或切到后台而丢失。

### 9.1 为什么推荐 Flutter

Flutter 官方支持从同一代码库构建 iOS 和 Windows，同时允许通过平台通道接入原生 API。它可以共享领域、数据和大部分界面代码，又能分别适配 iPhone 的触控训练流程与 Windows 的宽屏编辑流程。iOS 构建、签名和 App Store 发布仍必须在 macOS/Xcode 环境完成。

由于 Windows 已确定为桌面端，SwiftUI + CloudKit 不作为主方案；个人同步通过自有服务完成，避免 Apple 生态绑定。

### 9.2 客户端分层约束

- UI 不直接访问网络或 SQL。
- Repository 只暴露领域对象/DTO，不暴露具体云厂商 SDK 类型。
- 所有本地变更在同一事务内写业务表和 Outbox。
- 同步失败不回滚本地训练记录。
- 进阶算法是纯函数，可使用固定输入做单元测试。
- 平台差异集中在 Adapter；业务层不得判断 `Platform.isIOS`。

### 9.4 境内部署基线

首版推荐采用可容器化、云厂商中立的后端，而不是依赖境外 BaaS：

- API：Python FastAPI + SQLAlchemy 2 + Alembic，OpenAPI 作为客户端生成和合同测试的来源。
- 数据库：境内托管 PostgreSQL，部署在私有网络，不直接暴露公网端口。
- 媒体：通过统一 `ObjectStorage` 接口接入阿里云 OSS、腾讯云 COS 或其他 S3 兼容存储；客户端使用短时上传凭证直传，API 不转发大视频文件。
- CDN：只分发已发布的动作封面和视频；草稿原片保持私有。
- 后台任务：首版使用 Redis + 任务 worker，处理视频转码、封面、动作库 release 和数据导出；也可替换为云队列。
- API 与 worker 使用 Docker 部署；开发、预发布、生产使用独立账号、数据库、存储桶和密钥。
- 云厂商实现只存在于基础设施适配层，领域代码不得依赖 OSS/COS 专有 DTO。

### 9.5 登录与离线会话

- 私人 MVP 预置一个 Owner 账号，采用邮箱 + 密码登录；自助注册由功能开关控制，默认关闭。
- 密码只在服务端以 Argon2id 等合适的密码哈希保存，不保存或传输明文。
- 在线会话使用短时 access token + 可轮换 refresh token；每个 refresh token 绑定 `device_id`，支持在账号页面撤销单台设备。
- 首次登录必须联网。成功后服务端签发设备离线授权租约，默认 30 天；租约有效时即使 access token 过期或没有网络，用户仍可进入绑定账号的本地数据并训练。
- 离线租约到期后只能查看登录页和联网续期，不能新建训练；到期前至少 7 天提示用户联网，避免临场被阻断。
- Windows 支持本机 PIN/Windows Hello，iOS 支持设备生物识别作为本地解锁便利功能；它们不能替代首次服务端登录。
- 退出账号时撤销本机 token 和离线租约、清除本地解密密钥；本地数据库可保留为不可读的加密文件，明确选择“删除此设备数据”后才移除。
- 未来新增手机验证码或 Sign in with Apple 时，通过 `AuthProvider` 适配，不改变业务表中的稳定 `user_id`。

## 11. 同步协议

### 11.1 个人数据

采用 Outbox + 增量拉取：

1. 本地事务写入业务数据和 Outbox。
2. 客户端 `push` 一批幂等操作，每项带 `operation_id` 和 `base_revision`。
3. 服务端校验用户、权限和 revision，返回已接受/冲突/拒绝。
4. 客户端用游标 `pull` 服务端变更及 tombstone。
5. 合并完成后更新游标，再清理已确认 Outbox。

冲突规则：

- 训练组日志：不同 ID 追加合并；同一组被两端修改时保留两份修订并提示选择。
- 设置和普通备注：字段级最后写入胜出，但保留冲突审计。
- 计划结构：不自动逐节点拼接；产生冲突副本，让用户比较并选择/另存。
- 删除：软删除优先于旧 revision 更新；更新方可明确恢复为新 revision。
- 正在训练的会话：通过 `active_device_id` 和租约提示，不做强锁；用户可以接管并生成冲突副本。

### 11.2 公共动作库

- 客户端请求 manifest，携带当前 release 和客户端版本。
- 服务端返回无更新、增量包或完整快照，以及 SHA-256 和可选签名。
- 客户端下载到 staging 表，校验 schema、哈希、引用完整性和最低客户端版本。
- 单事务切换 active release；失败则继续使用旧版本。
- 媒体与元数据分离，封面可预取，视频按需缓存。
- 服务端可发布撤回清单；客户端立即隐藏或禁播被撤回内容。

用户私有动作与公共动作使用不同命名空间。公共动作更新不得覆盖用户私有副本。

## 12. API 契约草案

统一前缀 `/v1`，JSON 使用 camelCase 或 snake_case 必须全局统一；推荐 snake_case。错误响应包含稳定 `code`、可读 `message`、`request_id` 和可选字段错误。

### 12.1 同步与用户

```text
POST   /v1/auth/login
POST   /v1/auth/refresh
POST   /v1/auth/logout
GET    /v1/auth/devices
DELETE /v1/auth/devices/{device_id}
POST   /v1/sync/push
GET    /v1/sync/pull?cursor=...&limit=...
GET    /v1/sync/bootstrap
GET    /v1/profile
PATCH  /v1/profile
POST   /v1/account/export
DELETE /v1/account
```

`push` 必须支持批量、幂等键、部分成功和大小限制；`pull` 必须稳定分页，游标不能依赖客户端时钟。

### 12.2 动作库读取

```text
GET /v1/library/manifest?release=...&manifest_hash=...
GET /v1/library/snapshot/{release}
GET /v1/library/delta?after_release=...&through_release=...&limit=...
GET /v1/library/exercises/{id}/versions/{version}
GET /v1/library/media/{id}/access
```

`manifest` 返回的 `delta_after_release` 与 `delta_through_release` 是一次同步的固定范围；客户端分页时必须固定 `through_release`，且仅在所有页、所有动作版本和哈希校验成功后才更新本地 active release。服务端若发现中间 release 缺失或被撤回，会返回 `snapshot`；客户端应读取当前 manifest 对应的 snapshot，而不是猜测跳过缺失 release。

客户端主要从本地搜索，不应每输入一个字符就请求服务器。

### 12.3 桌面管理

```text
POST   /v1/admin/exercises
PATCH  /v1/admin/exercises/{id}/draft
POST   /v1/admin/exercises/{id}/media
POST   /v1/admin/exercises/{id}/submit-review
POST   /v1/admin/reviews/{id}/approve
POST   /v1/admin/reviews/{id}/request-changes
POST   /v1/admin/releases/preview
POST   /v1/admin/releases
POST   /v1/admin/releases/{id}/rollback
POST   /v1/admin/imports/validate
POST   /v1/admin/imports/commit
GET    /v1/admin/audit
```

发布、回滚和批量导入必须由服务端事务/后台任务执行，不允许客户端持有 `service_role` 密钥。

## 13. 桌面动作库管理流程

### 13.1 编辑器布局

- 左栏：状态、分类、负责人、更新时间筛选和动作列表。
- 中栏：基础信息、结构化步骤、提示/错误、安全说明、标签和关系编辑。
- 右栏：手机比例预览、媒体、校验结果、版本差异和审核记录。

### 13.2 状态机

```text
draft → in_review → approved → scheduled/published → deprecated/withdrawn
           ↘ changes_requested ↗
```

- 首版允许产品负责人审核并发布自己创建的内容；发布前必须逐项确认技术说明、安全提示、媒体版权、标签完整性和客户端预览，系统记录确认人、时间、清单版本及结果。
- 已发布版本不可编辑，只能复制为新草稿。
- `deprecated` 允许旧历史查看但不再推荐；`withdrawn` 用于安全或版权紧急撤回。
- 发布前自动检查必填项、标签、断链、媒体版权、哈希、引用环和客户端兼容性。

### 13.3 批量导入

- 支持 UTF-8 CSV/JSON + 媒体 ZIP。
- 先上传至临时区，只做校验和预览；明确提交后才写草稿。
- 报告必须精确到行、字段和错误码。
- 以稳定外部键去重，不按中文名称去重。
- 导出格式与导入格式对称，并附 JSON Schema 与示例。

## 14. 搜索与推荐

### 14.1 本地搜索

- SQLite FTS5（或等价全文索引）索引中英文名、拼音、别名、标签和器械。
- 支持简繁/大小写/空格归一化，拼音首字母作为辅助，不覆盖原文。
- 筛选器之间默认 AND，同一筛选器多选默认 OR。
- 排序综合名称命中、收藏、最近使用、可用器械和阶段匹配；规则可解释。

### 14.2 替代动作

先用编辑者维护的显式关系，再使用结构化标签匹配。替代建议至少满足记录类型兼容，并展示“为何相似/哪里不同”。

涉及疼痛时，不把标签相似度包装成康复推荐；只允许用户自行选择或展示已由专业人员审核的通用注意事项。

## 15. 安全、隐私与合规

- 全链路 TLS；访问令牌放系统安全存储，禁止写日志。
- PostgreSQL 所有面向客户端的个人表启用 RLS，策略校验 `user_id`；管理操作另走服务器权限。
- 每个账号使用独立的本地数据库并静态加密；数据库密钥放 iOS Keychain 或 Windows Credential Manager，不得从密码直接派生或写入配置文件。退出后没有解密密钥就不能读取旧账号数据。
- 对象存储私有原片使用短时签名 URL；发布媒体可用不可猜测、版本化路径。
- 日志和分析默认不包含训练备注、疼痛文字、令牌、邮箱和精确身体数据。
- 账户导出为版本化 ZIP（JSON/CSV + 媒体引用）；删除采用确认、撤销窗口、服务端清除任务和完成回执。
- 提供隐私政策、数据保留表、第三方处理者清单和备份恢复演练。
- 服务位于中国大陆。对公网开放前必须完成适用的 ICP 备案，并针对实际用户规模、数据类型和部署方式评估网络安全等级保护、个人信息保护、隐私政策和数据跨境要求；未经评估不得默认把个人训练数据传到境外服务。

## 16. 非功能指标

- 离线：已登录且离线授权有效的设备，断网时可建计划、搜索已下载动作、完整训练和查看本地历史。
- 可靠性：每次组记录在 200 ms 内本地持久化；崩溃重启可恢复未结束训练。
- 性能：普通设备冷启动目标 < 2.5 秒；本地动作搜索 P95 < 100 ms；训练页操作反馈 < 100 ms。
- 同步：重复提交不产生重复记录；在 10,000 条待同步操作下可分批恢复。
- 可观察性：API 有 request ID、结构化日志、延迟/错误率/队列积压指标；客户端有可导出的脱敏诊断包。
- 可访问性：动态字号不截断核心操作；交互目标至少约 44×44 pt；状态不只靠颜色表达。
- 兼容：每个动作库 release 声明最低客户端 schema；客户端至少保留上一个成功 release。

## 17. 关键边界与异常用例

开发和测试必须覆盖：

- 首次登录必须联网；已激活设备断网、离线授权过期、账号被远程停用后重新联网，以及用户退出后切换账号。
- 本地数据始终绑定创建它的账号和设备身份，切换账号时不能展示或上传前一账号的数据。
- 两台设备同时编辑同一计划；一端离线一周后恢复。
- 动作在计划创建后被改名、下架或紧急撤回。
- 训练进行中计划被另一设备更新；本次快照不改变。
- App 被系统杀死、来电、跨午夜、跨时区、夏令时变化。
- 休息计时器被多个动作/超级组触发；通知权限被拒绝。
- 单侧动作只完成一侧；组被跳过、失败、补录或事后修改。
- 哑铃按单只记录，杠铃是否含杆，配重片无法精确组成建议重量。
- 辅助引体等“数值增加但难度下降”的动作。
- 自重变化导致历史外部负荷和总负荷含义不同。
- 有氧的距离、时长、坡度、阻力、配速和心率不完整。
- 媒体无网络、下载中断、哈希不符、版权撤回或磁盘空间不足。
- 批量导入含重复 ID、循环进退阶关系、未知标签和超大媒体。
- 同步 token 过期、服务端游标失效、客户端时钟错误、API 部分成功。
- kg/lb 多次切换；只转换显示，不重写历史基准值。
- 用户删除账户但设备仍离线；下次联网必须阻止已删除账号继续上传。

## 18. 测试策略与验收

### 18.1 自动化

- 领域单测：计划版本、处方校验、单位/舍入、重量建议、替代动作规则。
- 属性测试：同步幂等、乱序操作、重复操作、单位往返和计划树序列化。
- 数据库测试：迁移升降级、RLS 隔离、软删除、审计触发器。
- API 契约测试：OpenAPI 请求/响应、分页游标、错误码和权限矩阵。
- 客户端集成测试：离线训练、崩溃恢复、后台计时、缓存清理。
- 视觉回归：iPhone 小屏/大屏、动态字号、Windows 常见窗口宽度与显示缩放比例。
- 发布包测试：从 N-1/N-2 客户端升级动作库和数据库。

### 18.2 MVP 验收场景

1. 已激活设备进入飞行模式后，从本地动作库创建一个含热身、主项、辅助和有氧阶段的单次训练计划并完成记录。
2. 同一账号在桌面修改计划，iPhone 同步后看到新版本，旧训练历史保持不变。
3. 一个动作从草稿完成审核并发布，客户端增量更新后可搜索、查看文字和离线封面。
4. 完成三组目标训练后出现有依据的下次重量建议；拒绝建议不会再次强制应用。
5. 两端同时修改计划时不丢数据，并产生可理解的冲突处理界面。
6. 删除/撤回动作后，历史记录仍能解释当时做了什么，新计划收到替换提示。
7. 用户可导出全部个人数据，导出的组记录能与界面数量核对一致。

## 19. 分阶段实施与 Agent 分工

### 阶段 0：契约与工程基线（2–4 天）

- 将第 3 节已确认决定写入 ADR，确定最低系统版本、术语表和隐私威胁模型。
- 冻结 v1 领域模型、OpenAPI、内容 JSON Schema、设计 token。
- 输出 20–30 个经过审核的种子动作，覆盖所有记录类型。

### 阶段 1：离线 MVP（3–5 周）

- Flutter 外壳、响应式设计系统、本地数据库与迁移。
- 动作库浏览/搜索/详情、计划编辑器、训练执行、崩溃恢复。
- 基础历史、双重渐进建议、JSON/CSV 导出。
- 暂用打包动作库，不依赖服务端即可完成主流程。

### 阶段 2：账号与同步（2–4 周）

- Auth、RLS、Outbox push/pull、冲突副本、设备管理。
- 服务端监控、备份、账户导出/删除。
- 多端端到端故障测试。

### 阶段 3：动作库后台（2–4 周）

- 桌面编辑器、媒体上传/转码、审核状态机、批量导入。
- release manifest、增量包、校验、灰度、回滚和紧急撤回。

### 阶段 4：质量与扩展

- 更完整分析、日历提醒、可选 HealthKit、更多进阶算法。
- Windows 安装器/签名/自动更新完善、本地化、无障碍和性能专项。

| 工作包 | 交付物 | 前置依赖 |
|---|---|---|
| A 领域与数据 | Dart 领域模型、SQL migration、JSON Schema、种子数据 | 阶段 0 决策 |
| B 设计系统与导航 | token、组件库、iOS/桌面响应式壳、视觉回归基线 | 术语和导航冻结 |
| C 动作库客户端 | 本地导入、FTS、筛选、详情、媒体缓存 | A、B |
| D 计划编辑与执行 | 计划树、拖放/键盘、快照、组记录、计时恢复 | A、B、C |
| E 进阶与分析 | 策略接口、建议解释、趋势和 PR 重建 | A、D |

### 19.1 Agent 模型与思考强度基线

为了保证质量，端到端主执行模型最低使用 `gpt-5.6-terra`。`gpt-5.6-luna` 只承担边界明确、能自动验收的机械任务，不能独立负责架构、同步、安全、训练领域逻辑或最终集成。

| 工作 | 最低模型 | 思考强度 | 说明 |
|---|---|---|---|
| 主协调、阶段规划、跨包集成 | Terra | `xhigh` | 负责契约一致性、依赖顺序、冲突处理和完成判定 |
| A 领域与数据 | Terra | `xhigh` | 版本、快照、单位和迁移错误会产生长期数据债务 |
| B 设计系统与普通页面 | Terra | `high` | 组件实现可降到 Luna，但交互和响应式验收仍由 Terra 完成 |
| C 动作库客户端 | Terra | `high` | 搜索、缓存和状态边界需要综合判断 |
| D 计划编辑与训练执行 | Terra | `xhigh` | 属于核心状态机，涉及崩溃恢复和历史事实 |
| E 进阶与分析 | Terra | `xhigh` | 算法必须可解释、可测试并遵守训练安全边界 |
| F 后端、登录、同步与权限 | Terra | `xhigh` | 不允许 Luna 独立实现或审批 |
| G 内容后台 | Terra | `high` | 发布、撤回、回滚路径升到 `xhigh` |
| H 自动化测试/DevOps | Terra | `high` | 威胁模型、RLS、恢复演练和发布门禁升到 `xhigh` |
| I 内容格式化、种子数据录入 | Luna（可选） | `high` | 仅限按既定 schema 转换；内容正确性由产品负责人审核 |
| 最终发布审查 | Terra | `xhigh` | 最低要求；若可用，推荐另用 Sol `high/xhigh` 做独立复核 |

不建议整项目统一使用 `max/ultra`：它们应留给难以复现的同步冲突、数据库迁移、安全审计或最终疑难问题。常规实现用 Terra `high`，关键路径用 Terra `xhigh`，再以测试、契约和独立审查保证质量，通常比单纯提高所有任务的思考档位更可靠。

## 20. 首版完成定义

满足以下条件才能称为可发布，而不只是“界面完成”：

- 第 18.2 节七项验收全部通过。
- 已激活且离线授权有效时，无网络和服务端故障不会阻止本地训练或造成数据丢失。
- RLS 越权测试、令牌泄漏扫描、依赖扫描无高危未处置项。
- 动作内容有作者、审核、版权和版本记录；没有无授权抓取媒体。
- 线上数据库和对象存储有已验证的恢复流程。
- App 的隐私说明、数据导出和账户删除可实际使用。
- iOS 与 Windows 均完成真实设备测试、签名和升级测试。
- 已知限制、支持渠道、崩溃和 API 告警负责人明确。
